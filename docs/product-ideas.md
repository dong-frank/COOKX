# COOKX 产品想法与讨论记录

更新日期：2026-11-17

本文持续记录产品讨论。明确区分用户已提出的需求与讨论中的建议；建议不代表已经确定的开发范围。当前仍处于产品构思阶段。

## 一、已提出的产品方向

COOKX 是一个从记录菜谱出发的 Android App。记录菜谱是核心功能，家庭点菜、食材管理和 Agent 等功能围绕菜谱展开。

### 1. 菜谱与做菜辅助

- 通过一道菜的图片进入详情，查看所需食材、上次制作时间。
- 点击“开始制作”进入做菜辅助模式。
- 辅助模式类似 PPT，每一页展示一个步骤及说明。
- 模式内提供做菜时常用的工具，例如计时器。
- 完成后支持拍照上传菜品照片。
- 记录本次制作的评价，例如难易程度、口味等；具体评分项目和尺度待讨论。
- 制作时间按“日期＋餐次”记录，不要求精确到时分。餐次为早餐、午餐、晚餐、夜宵。
- 点击“开始制作”时，根据设备本地系统日期与时间预选日期和餐次，支持手动修改；完成时沿用选择，不因跨越时间分界而自动改变。
- 初始餐次范围：05:00–10:00 早餐、10:00–15:00 午餐、15:00–21:00 晚餐、21:00–次日05:00 夜宵，均包含起点、不包含终点。
- 菜谱制作过程分为“备菜”和“烹饪”两大阶段，各阶段由有序的小步骤组成。
- 每一步有对应操作的图标，例如清洗、切块、切片、切丁、焯水。
- 步骤分为“标准操作模板步骤”和“自定义步骤”。保存常见的标准操作作为可复用模板，例如“切滚刀块”“肉类焯水”；模板包含具体做法，而不只是操作名称或图标。
- 初期不采用菜谱嵌套或引用子菜谱，步骤仅保留上述两类。
- 用户给出的肉类焯水模板示例为“冷水肉下锅，加一勺料酒”，用于说明模板所承载的内容，不代表所有肉类或菜谱必须采用同一做法。模板字段与套用规则见第二部分建议。
- 标准操作模板支持参数化设置，例如腌制时长、食材及调料用量可在套用时填写或调整，不固定为所有菜谱共用的时间与用量。具体参数类型、默认值和必填规则待讨论。
- 所有标准操作模板延续可参数化配置的思路；初期不要求过度精确，时间、用量等按菜谱需要填写，允许“适量”等原文，不强制精确数值或大量细项。可选动作按需启用，保留清楚、可执行的核心流程。
- 创建菜谱时按这套阶段与步骤结构录入；开始制作后的 PPT 式辅助页面逐步展示同一套步骤细节。
- 后续 Agent 从小红书帖子结构化提取菜谱时，也使用这套结构；未来可探索由 Agent 调度安排共通的备菜操作，当前不实现调度。

### 2. 家庭与点菜

- 从产品最初版本就引入家庭概念，家庭是基础产品概念。
- 一个人也可以组成家庭，单人使用和多人家庭使用都在这套概念下成立。
- 每个用户可以创建家庭。
- 其他用户通过家庭邀请码加入家庭。
- 家庭共用一本菜谱，菜谱以家庭为归属。
- 家庭成员可以对菜谱进行点菜和打分。
- 成员退出家庭及退出时复制菜谱的功能初期不考虑。后续方向为成员退出时可选择复制菜谱，具体范围和规则届时讨论。
- 家庭数量、角色、菜谱编辑权限、点菜处理方式及评分归属待讨论。

### 3. “囤囤鼠”食材管理

- 记录每次购买食材的花费。
- 记录冰箱剩余食材量。
- 记录调料台的情况。
- 囤囤鼠场景选用与冰箱同系列的三层调料架，点击查看调料情况；冰箱在画面靠左，右侧放落地桌，桌面承托调料架。落地桌具体选型及详情交互仍供评审。
- 库存如何录入和更新、采用何种计量方式、是否与做菜自动联动待讨论。
- 冰箱界面打开后显示现有物品及每项数量，不显示没有库存的物品；数量的计量、录入与维护方式继续讨论。

### 3.1 准备食材与采购便签

- 菜谱页面的“准备食材”作为可点击入口，点击打开采购备忘便签，方便去超市采购时查看。
- 便签按项列出所需食材，每项支持打勾处理。
- 勾选或取消勾选仅改变备忘状态，不修改库存数量，不生成采购入库或花费记录；相关操作另设入口，具体交互待设计。
- 与囤囤鼠联动：家里已有对应食材时，该项默认勾选。
- 库存匹配、数量不足时的处理、勾选状态保存与库存更新关系，见第二部分待确认建议。

### 4. 小红书内容导入

- 希望接入读取小红书帖子。
- 希望将小红书经验帖子转换为可以使用的菜谱。
- 内容获取方式、支持的帖子类型和实际接入能力尚未验证，当前不承诺任意链接均可读取。

### 5. Agent

- 根据用户一天做的菜，提供健康相关的建议。
- 协助处理食材与调料的替换。
- 协助将小红书经验帖子转换成菜谱。
- 建议如何确认和保存、Agent 是否可以直接修改记录、使用哪些用户数据待讨论。

### 6. 菜谱标签

- 菜谱支持添加标签，例如“快手菜”“川菜”“粤菜”“宴客必备”“拿手菜”“高难度”。
- 系统提供预设标签，同时支持用户自定义标签。
- 首页左侧分类使用标签，不再另设一套独立分类。
- 家庭可以选择在左侧展示的常用标签，并调整展示顺序。
- 同一道菜支持多个标签，可以出现在多个标签对应的列表中。
- 标签管理权限、分组及多标签组合筛选规则尚待讨论。

## 二、建议的产品组织方式（待确认）

### 1. 以一次做菜形成核心闭环

记录或导入菜谱 → 查看食材 → 开始制作 → 分步辅助与计时 → 完成拍照、评价 → 下次参考历史。

建议首个可用版本在家庭概念下优先完整走通这条流程。库存和 Agent 的具体能力可后续分阶段接入；家庭从最初版本就存在，具体协作功能的交付范围待讨论。

建议首次使用时提供“创建家庭”和“加入家庭”入口，独自使用的用户也可以创建只有自己的家庭。是否自动创建默认家庭、是否要求立即命名，以及具体引导方式尚未确定。

### 2. 将菜谱与每次制作记录分开

- **菜谱**：菜名、封面、食材、用量、步骤、来源等可复用内容。
- **制作记录**：某一次制作的日期与餐次、照片、实际替换、评价和备注；日期与餐次已确定，不要求用户记录精确时分。
- “上次制作时间”由制作记录产生，建议展示为“昨天 · 晚餐”或“11月17日 · 午餐”，历史照片和评价也能按次回看。
- 做完后可以选择把经验修改到菜谱，避免一次临时替换直接覆盖原配方。

餐次交互（已确定）：

- 保留制作日期，默认今天，日期与餐次均支持手动修改。
- 点击“开始制作”时按设备本地系统时间预选餐次，完成时沿用该选择，避免长时间烹饪导致餐次自动改变。
- 自动预选可手动修改；用户修改后不再被自动判断覆盖。提前备餐时可选目标餐次。
- 初始时间范围：05:00–10:00 早餐、10:00–15:00 午餐、15:00–21:00 晚餐、21:00–次日05:00 夜宵，均包含起点、不包含终点。这只是便捷默认值，不代表用户固定的作息。
- 日期按设备本地日历日期预选，凌晨夜宵也可通过手动修改日期记到前一天。
- 此调整针对制作记录的时间表达，做菜步骤的计时器仍按实际时长工作。

补记历史制作记录的独立入口与具体交互仍待设计。

### 3. 将做菜者评价与家庭成员评价分开

- 做菜者记录制作体验，例如难易程度、是否成功和下次改进点。
- 家庭成员记录用餐反馈，例如口味与想不想再吃。
- 家庭成员可对菜谱表达点菜意愿；是否同时支持对某一次成品评价，待讨论。

### 4. 做菜辅助围绕厨房实际操作设计

- 大字、清楚的步骤编号、容易触达的上一步和下一步。
- 当前步骤直接展示本步所需食材与用量，减少返回详情查找。
- 计时器与步骤关联，切换步骤后仍能继续计时；多计时器需求待讨论。
- 支持中途退出后继续；进入辅助模式时是否保持屏幕常亮，待设计。

### 5. 库存维护从低负担开始

- 可先讨论“充足／不多了／用完了”等粗略状态，减少每次称重录入的负担。
- 购买记录、库存状态和调料余量可以独立维护，再讨论自动扣减与补货提醒。
- 若支持做菜后扣减，需允许用户确认实际消耗及替换，避免库存误差不断累积。

### 6. Agent 的输出可核对、可修正

- 导入菜谱时保留原帖来源；缺失或推测的用量、时间等信息明确标记，并由用户确认后保存。
- 替换建议说明适用条件，以及可能需要调整的用量或做法。
- “做过的菜”与“实际吃了什么”分开记录：家庭共享、人数和食用份量会影响饮食分析；信息不足时不输出精确的个人营养结论。
- 用户确认后再将建议应用到菜谱或库存，具体自动化范围待讨论。

### 7. 标签组件的补充建议（待确认）

- 同一道菜允许添加多个标签，表达菜系、场景、耗时特点、难度和家庭经验等不同维度。
- 建议系统预设标签供各家庭选用，自定义标签由当前家庭共享，便于所有成员用同一套词整理菜谱。
- 预设标签少而精，支持搜索；输入不存在的标签名时可直接创建，避免打断录入。
- 添加标签时先匹配已有名称，减少同名重复；自定义标签可重命名、删除。删除标签只解除关联，不删除菜谱；从单道菜移除标签不影响其他菜谱。
- 首期建议使用平级标签，界面可按“菜系”“场景”等分组展示预设项；暂不要求用户维护层级或填写每个维度。
- 标签用于详情展示、编辑和筛选；首页继续遵循已有约定，菜品行仅显示图片和名称，不自动增加标签。
- 左侧按家庭选择的常用标签及顺序展示，依据第一部分已确定的标签方案；“全部”入口、未打标签菜谱的入口及排序交互方式仍待设计。
- 多标签筛选建议明确表达“同时符合”或“符合任一”；例如“川菜 + 快手菜”可用来找同时满足两个条件的菜，默认规则待确认。
- “高难度”等标签用于概括菜谱特点；每次制作后的难度评分属于制作记录，两者不自动互相覆盖。
- “拿手菜”可能指家庭擅长，也可能指具体成员擅长；首期可先作为家庭标签，个人擅长关系若需要再单独设计。
- 后续 Agent 可提出标签建议，用户确认后添加；不自动把推测作为已确认标签。

### 8. 菜谱阶段与步骤的数据结构建议（待确认）

两阶段、逐步记录、步骤图标、标准模板与自定义步骤两类，以及创建与播放共用结构已确定。以下具体字段与交互为讨论建议：

- 菜谱包含基础信息、食材清单、备菜步骤列表、烹饪步骤列表。两个阶段使用同一种步骤结构，仅所属阶段不同；允许某个阶段暂时没有步骤。
- 步骤建议包含：稳定标识、步骤种类（标准模板／自定义）、操作类型、标题、详细说明、关联食材及本步用量、可选操作参数、可选计时器时长、可选图片。标准模板步骤额外保留来源模板标识及版本。顺序由阶段内列表表达。
- 操作类型使用可识别的标准值，图标由操作类型映射。初期可将清洗、切块、切片、切丁、焯水、腌制、翻炒、炖煮、调味、装盘等作为候选；最终预设清单待定。
- 自定义步骤自由填写标题与说明，可以选用已有操作图标；无法匹配操作类型时使用“其他”及通用图标。自定义步骤不等于必须使用未知操作类型。
- 食材关联引用菜谱食材条目，而不只写在说明中；同一食材可被多个步骤使用。各步用量可为空，“适量”等原文也可保留，不强迫用户填写精确数值。
- 时间、火候、温度、切制尺寸等按需要填写；计时器时长与说明中的时间要求分开考虑，例如“水沸后再计时”的启动条件不能省略。最初不要求用户逐项填写所有参数。
- 阶段由菜谱作者指定，不由操作类型固定决定，例如焯水可放在备菜阶段，也可按原做法安排在烹饪阶段。
- 原则上一页表达一个主要动作；紧密关联的手法可保留在说明中，避免把步骤拆得过碎。复杂做法通过拆步表达，不要求每一步必须简化成一个关键词。
- 创建时先选阶段，再选择“使用标准操作”或“自定义步骤”；前者套用模板并关联食材、填写所需参数，后者自由填写标题与说明并选择操作图标。支持阶段内增删、排序及跨阶段移动。
- 制作模式按“备菜列表 → 烹饪列表”逐页展示；每页呈现阶段、步骤进度、图标、标题、说明及本步食材，存在计时配置时展示启动入口。
- 制作中的完成状态、计时器运行状态属于当次制作，不写回菜谱步骤模板。
- Agent 导入先形成可编辑草稿，使用与手动创建相同的操作类型与食材关联；未识别操作使用兜底类型，缺失信息和推测内容标记待确认，不凭空补成确定值。
- 保留步骤的独立标识与食材关联有助于后续扩展调度；跨菜谱依赖、产物状态、并行任务与合并操作等完整调度模型留到后续讨论。操作名称相同不意味着可以直接合并或互换顺序。

标准操作模板与菜谱步骤的关系建议（待确认）：

- 模板库独立保存可复用做法，模板建议包含标识、版本、名称、操作类型／图标、默认说明、适用食材或条件、可填写参数及默认值，以及可选计时配置和图片。
- “操作类型”用于识别动作和选择图标；“模板”描述一种可复用的具体做法，例如切块类型下可以有“切滚刀块”模板。步骤的两类按是否来自模板区分，不按是否拥有标准图标区分。
- 应用到菜谱时生成具体步骤，关联该菜谱食材，并保存当时的模板内容副本与填写参数；保留来源模板标识和版本。修改或删除模板不自动改变已有菜谱。
- 默认做法可直接套用；尺寸、用量等作为可调整参数。若要改写核心做法，建议转为自定义步骤，可保留原模板来源用于追溯，具体转换交互待定。
- 模板中的辅料也需在应用时关联或加入菜谱食材清单，避免步骤要求加入料酒而食材清单遗漏。缺失关联可提示用户补充，不自动当成已具备。
- 单个标准模板步骤可以包含围绕同一目标的紧密动作，例如肉类焯水中的冷水下锅与加入料酒；若需多页引导，拆为多个步骤。首期不引入模板内部嵌套步骤。
- 标准模板步骤与自定义步骤保存后都具有完整可展示内容，制作模式可按相同方式逐页展示。
- Agent 后续优先匹配做法兼容的模板并填写参数；不匹配时生成自定义步骤。不得仅因标题相同就用模板覆盖原帖里的不同做法。
- 模板初期由谁维护、是否同时支持系统模板和家庭模板、是否允许将自定义步骤另存为模板，仍待讨论。

### 9. 采购便签与库存联动建议（待确认）

- 从菜谱食材清单生成便签，包含食材名称、菜谱所需用量和勾选状态；调料如果在菜谱食材清单中，也纳入检查。
- 勾选统一表示“本项已准备，无需再购买”，可由“家中已有”自动预选，也可由用户采购后手动勾选；建议以小字区分“家中已有”和“手动勾选”，避免将两者都表示成“已购买”。
- 有库存记录不一定数量充足。能比较数量且单位兼容时，建议足量才默认勾选，不足时显示缺口；库存数量不明或单位不可比时，提示“家中有，余量待确认”，是否仍按已有食材默认勾选的具体规则待讨论。
- 食材匹配尽量基于统一食材标识；未建立标准食材库时优先使用确定匹配，不把可能不同的食材或替代品静默视为同一种，允许用户修正关联。
- 便签保存用户勾选状态，重新打开可继续使用；库存更新不应悄悄覆盖用户手动选择，可提供“按库存重新检查”。便签是否支持重置、重复采购、多次制作及家庭成员共同勾选，仍待讨论。
- 已确定：勾选或取消勾选仅改变备忘状态，不自动增加或扣减库存，不生成采购入库或花费记录。采购入库、花费记录及做菜消耗的具体操作仍需单独设计。
- 制作完成状态与采购便签勾选状态分开，便签全勾选不代表已经做完菜。
- 初期可先围绕单道菜生成便签；多道菜合并采购、同类食材汇总及独立采购清单入口可作为后续方向，尚未确定。

### 10. 菜谱嵌套／引用子菜谱提案（初期不采用）

用户已决定初期不采用该设计，原因是复杂度过高。当前不增加引用菜谱步骤，也不为初期数据结构引入嵌套及其配套机制。以下仅保留历史提案，不作为当前需求或待落实方案。

- 用户提出：菜谱可以作为一个步骤嵌入其他菜谱，例如西红柿炒鸡蛋引用炒鸡蛋菜谱。
- 建议在标准模板步骤、自定义步骤之外，增加“引用菜谱步骤”：标准模板复用一个操作，子菜谱复用一组完整的有序步骤与食材。该方案尚待用户确认，不据此变更既有实现。
- 引用时需说明引用对象、用量／份量，以及目标产物状态。例如西红柿炒鸡蛋需要的是供后续合炒的炒蛋，不一定适合直接引用含完整调味与装盘的独立炒鸡蛋菜谱；可单独保存“炒蛋底”等适合复用的基础菜谱。
- 父菜谱仍分备菜、烹饪阶段，引用节点放在作者指定的位置。制作时建议在当前位置展开子菜谱步骤，保留层级提示，完成后返回父菜谱；暂不自动把子菜谱备菜移到父菜谱开头或重新调度。
- 引用子菜谱与标准操作模板内部的动作说明是不同概念；既有单页模板不因该提案自动改为多页嵌套。
- 采购便签应汇总父菜谱与被引用子菜谱的食材，按份量换算，并仅在食材和单位可确定兼容时合并；需避免同一份原料被父子菜谱重复声明、重复统计。
- 引用应禁止直接及间接循环，例如 A 引用自身或 A 引用 B、B 再引用 A。初期可考虑只开放一层引用，具体深度待确认。
- 建议明确引用版本或保存内容副本，防止子菜谱编辑后父菜谱做法静默变化；具体更新机制待讨论。
- 建议执行子菜谱时归入父菜谱当次制作，不默认生成第二次独立制作记录；是否更新子菜谱的上次制作日期和评价需另行确定。
- 完整模型可预留引用能力，首期是否实现、基础菜谱是否出现在普通首页、引用份量与阶段展开的具体交互仍待讨论。

## 三、优先讨论的问题

1. **主要录入方式**：手动整理自己的菜谱，还是以小红书等外部内容导入为主？
2. **点菜含义**：表达“想吃”，还是提交某天、某顿的用餐请求？
3. **库存精度**：精确数量，还是容易维护的余量状态？
4. **标准操作模板维护**：初期只提供系统预设模板，还是同时允许家庭创建自己的模板？
5. **采购默认勾选**：库存只确认“有”但数量不明时，默认勾选并提示核对，还是待用户确认足量后勾选？
